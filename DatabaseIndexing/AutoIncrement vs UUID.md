# Auto Increment
- Its a counter automatically generated by database. Whenever we insert a row to a table, database increments this internal counter and assigns it to the row.
- A normal int counter takes 4 bytes (32-bits) and bigint counter takes 8-bytes (64-bits).
## Advantage
- Storage Efficiency. Since these counters takes 32-bits/64-bits, so they take less space compared to UUID which takes 128-bits.
- Index Performance. Since counters are always increasing, new rows simply goes to the right-most node in the index b+ tree. This is simple and predictable and reduces node splits. And hence, better write performance.
- No library needed.
- Integer comparisons are faster than string-based UUID.

## Disadvantages
- Not distributed safe. If we have multiple database shards, each database shard will manage its own counters. So, there will be collisions for sure. For example, If a user creates a profile and its handled by shard A - shard A assigns this user profile an ID of 1. Now, another user creates his profile, this time its handled by shard B - shard B assigns it an ID of 1 as well. So, we see two users were given the same ID. We will need some kind of coordination between the two shards to avoid this. For example: shard A will be configured to have only even IDs and shard B will be configured to have only odd IDs. But this setup might break if we add or remove new shards. We could also consider having a central coordinator that generates the next ID number. But again, this central coordinator may become a bottleneck and SPOF.
- In case if we ever have to merge multiple databases, we will get ID conflicts.
- Since the IDs are auto-incremented, so they are predictable and guessable. For example if our API looks like this: `/users/123`. A malicious person can easily try to access `/users/124`.
- We can easily enumerate all the users through the API like in the last point and hence easily get data about how many users exist in a business. Hence, business data may be at risk. This is also called "**German Tank Problem**".
- The counter is managed by database only. The next ID is generated only after we insert a row. We cannot generate it ourselves.
- We cannot perform idempotent retries easily. If a network request fails, and we cannot confirm if the insert succeeded, retrying may create a duplicate of the same record with different IDs. With UUIDs, we generate the ID client-side first, so a retry with the same ID will not mean duplicate records.

# UUID (Universally Unique Identifier)
- A 128-bit identifier represented in hex value.
- We have several versions: v4 is fully random, v7 is time-ordered.
- A UUID is generated by an algorithm without any central coordinator.
- It generates a globally unique ID. So no matter where you are, if you generate a UUID, you'll get a unique one. The chances of collision is practically 0.
- Always store UUIDs as native UUID or binary type, never as a string. Because if we store it as strings, it will take up more space (36 bytes).
  
## Advantages
- Distributed safe. Multiple machines can generate unique IDs independently without any coordination and collision.
- No ID conflicts on database merges.
- Client-side generation. We can generate a UUID anywhere. On frontend and backend both. This can be very useful in optimistic UI updates.
- Not predictable. So no business data leaks.

## Disadvantage
- Each UUID takes 128-bits. Which is a larger than 32-bit/64-bit counter. So, more storage usage.
- Since UUIDs(v4) are random, so they can go anywhere in the B+ tree index tree. Which can lead to more node splits, which can be expensive. So, slower write performance.
- Not human friendly.
- Since generating a UUID uses an algorithm, so slight overhead.

# UUID v7 - Best of both worlds
- It is time-ordered. The first 48-bits are millisecond timestamp, followed by some random bits.
- This means, now, UUID is ordered just like auto-increment. Hence, during index inserts, the new row goes to the right-most node, reducing node splits and hence improving write performance. This was one of the main problems with pure random UUID, which is fixed in this version.
- Since, we have some randomness, so still not guessable and not predictable and globally unique.
- For most new systems today, UUID v7 is recommended.
