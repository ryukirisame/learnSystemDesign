# Distributed Locking

## Without Locking
- Lets suppose we have a movie ticket reservation platform. There is only one last seat available: seat-5.
- We have two users A & B who want to book a seat. They both fetch available seats. Both of them see seat-5 is the last remaining seat.
- Both the users hit "Book" button simulataneously. A's request went through Node 1 and B's request went via Node 2.
- Node 1 checks if the seat is available or not. Currently its available, so it proceeds with booking seat-5. Payments etc.
- Meanwhile, Node 2 also does the same. It checks if the seat is available - finds it to be available. Proceeds with the payment and marks the seat as booked.
- Two Nodes marked the same seat as Booked.
- This is the problem.

We need a way to make sure that only **one** node can proceed with booking a particular seat at a time. This can be done with Distributed locks.
- Distributed locking is a mechanism through which we allow only one node to work on a shared resource at a time. Read operation is fine. Write operation is not.
- The idea is simple: whoever gets the lock proceeds, everyone else waits or backs off.

## With Distributed Lock
Let's try the same scenario with distributed locks.

- We have the last remaining seat: seat-5.
- A & B both try to book the seat simultaneously.
- Node 1 received A's request and Node 2 received B's request.
- Both node will now race to acquire a lock on seat-5.
- Let's suppose Node 1 won. Node 1 will now proceed with payment. Node 2 is the loser. So it will fail the booking and tell the user that someone else is booking that particular seat.
- Node 1 succeeds with payment and marks the seat as Booked.
- User B will not be able to get the seat. No payment was done by User B. No double booking here.

## Why do we need distributed locks?
- We have studied concurrency locks in OS. Like semaphores and mutex locks. They are applicable only for multiple threads inside a single process.
- In a distributed system, we have multiple processes on multiple machines that can all try to do something at the same time. There's no shared memory. The OS can't help us.

### Purpose of distributed locks
- **Efficiency Purpose**: When we simply want to avoid doing the same work twice. Like for example sending email twice. It's okay if this slips occasionally.
- **Correctness Lock**: Two nodes/clients must never do the same work simultaneously - otherwise it will lead to data integrity issues. 

### Efficiency Lock Scenario
- Imagine that we have a business. We sell stuff online.
- Every midnight, we have a backend service which runs and analyses the day's sales, creates detailed reports in a PDF and uploads to S3. All of this in background.
- Let's suppose that we have three backend nodes to handle high traffic during the day. Each of these nodes contains the analysis service code as well. This service gets invoked at midnight 12AM automatically.
- Now let's suppose the time just hit 12AM. All the three nodes will wake up to do the job. All three of them analyses the database, creates a pdf report and uploads to S3.
- But this is duplicate work. Only one of them could do it. Why do it three times?
- This is where distributed locks come in. If we apply distributed locks then this is how it will go:
- All nodes will wake up at midnight 12AM and all three of them will race to acquire a lock for the job.
- The node which wins, will proceed with doing the job, the rest of the nodes will backoff. They won't proceed with the job.
- So you see, we just made our system more efficient. We avoided all three of the nodes doing the same work. Because the end result is the same - the report. No matter who does it, it's gonna be the same.

### Correctness Lock Scenario
- The movie seat scenario at the start of this file.

# Properties of Distributed Locks
So, if we implement distributed locks, what are the criterias it should pass to be considered a distributed lock.
- Mutual Exclusion: No two nodes can hold a lock on the same resouce. Only one node can acquire a lock on the resource at any given moment.
- Deadlock Free: The node which acquires the lock, must eventually release it. So that even if the lock holder crashes, atleast others can proceed and not wait indefinitely for the crashed node to release the lock.
- Fault Tolerant: The lock service itself (The one who provides the lock - DB, Redis, Zookeeper etc), should not be a SPOF.
- A node cannot accidently release someone else's lock.

# Distributed lock Implementations
## 1. Database-Based Locks

- The idea is simple: Have a table named `DISTRIBUTED_LOCKS` with a schema like the following:
  - ``` 
    CREATE TABLE distributed_locks (
    resource_name VARCHAR(64) PRIMARY KEY,
    locked_by VARCHAR(128) NOT NULL,
    expires_at TIMESTAMP
    );
    ```
- When a node wants to acquire a lock on a resource, it will simply try to create a row in `distributed_locks` table.
```sql
 INSERT INTO distributed_locks (resource_name, locked_by, expires_at)
VALUES ('seat:5', 'node-3', NOW() + INTERVAL 30 SECOND)
```
- If the insert succeeds, that means the node have now acquired the lock.
- If the insert fails (because of primary key constraint), that means the resource is locked by another node.
- When a node wants to release the lock, it simply deletes the row from the table.
```
DELETE FROM distributed_locks
WHERE resource_name = 'seat:5' AND locked_by = 'node-3'
-- The `locked_by` check prevents releasing someone else's lock
```

### Analysing this implementation
- Mutual Exclusion: No two nodes will be able to get the lock on the same resource as they will not be able to create the row with same resource name twice. PASSED.
- No Deadlock: The node must release the lock. Well, for that the implementation must ensure that we run a cleanup service which deletes those rows whose `expires_at` has come to pass. Something like: `DELETE WHERE expires_at < NOW()`.
  - Please Note: A node can(and should) first check if the existing lock has already expired or not. If it has already expired, it can delete it and then insert it's own. So it becomes a two-step process and must be **ATOMIC**. This ensures no false lock and reduces dependency on the cleanup service - in cases where the cleanup service itself crashes.
- Fault Tolerance: The lock service - DB can become a SPOF if we have just one instance of DB with the `distributed_locks` table. For this, we can replicate our DB. But then we might run into eventual consistency issue, which will lead to more issues. If we have a distributed database with strong consistency guarantees (synchronous replication), only then this criteria passes. 
- Fairness: While releasing the lock by deleting the row, let's make sure the node can only delete those rows whose `locked_by` field is same as itself. `... AND locked_by = 'node-3` This extra check in delete query will take care of fairness.

### Pros 
- Simple.
- No another infrastructure required.

### Cons
- DB can become a bottleneck and cannot scale well.
- SPOF if a single DB instance is used.
- A separate cleanup process is required to release the locks.


## 2. Redis Single-Node Lock
- Redis is fast. And all of its operations are Atomic by default because Redis is single-threaded.
- Let's suppose we have two nodes: A and B. We also have a single Redis node.
- Both A and B will race to create an entry in Redis using the following command:
```
SET lock:resource_name locked_by NX PX 30000
```
- `NX` option: Create the key only if it does not exist. If it already exists, fail.
- `PX` option: TTL time in milliseconds. We could have also used `EX` which takes TTL in seconds instead of milliseconds.
- TTL ensures that no node holds the lock indefinitely.
- `locked_by` is a unique identifier of the node. 
- The node which is able to create the entry first, gets the lock. The node which could not create the key will either wait or go home.
- To release the lock, simply delete the key. But we must ensure that only that node deletes the key who has acquired the lock.

### GC Problem
Lets consider the following scenario:
- Node A acquires the lock for 30 sec.
- Node A is now working on the resource.
- After like 20 sec, a Garbage Collection occurs in node A which freezes Node A for 40 secs.
- Meanwhile, TTL for Node A lock expires and is removed by Redis.
- Node-B acquires the lock by creating an entry.
- Node-A wakes up from GC and still thinks it holds the lock and continues the work on the same resource! => Problem-1
- If Node-A is programmed to release the lock manually after completing its work, then it will blindly do: `DEL resource_name`, releasing Node-B's lock => Problem-2

#### The fix
The node must first check if the lock it's trying to delete belongs to it or not. So it becomes a two-step process: 
1. Check if the lock belongs to it - check the `locked_by` identifier.
2. Delete the Redis key.

- These two must be done atomically.

### Analysing this implementation
- Mutual Exclusion: No two node can create the same key using NX option. PASSED.
- No Deadlock: TTL ensures no deadlock. PASSED.
- Fault Tolerance: Since we have a single redis node, so this becomes a SPOF. FAILED.
  - If we somehow use Redis persistence with synchronous persistence, or Redis cluster (Master-Slave) with synchronous replication, then only it will pass. But Redis uses the asynchronous mechanism. That's why the creator of Redis created another method itself - Redlocks.
- Fairness: The GC problem showed us how a node can release another's lock. The fix of it must be applied. Then it is PASSED.  

### Pros
- Very Fast (~ms)
- Simple
- Widely understood

### Cons
- Single Node - SPOF.
- If the Redis node restarts, all locks are lost. If it recovers the locks from persistence layer on restart - some old locks may re-appear because Redis persistence is asynchronous and the data was not up-to-date at the time of crash.
