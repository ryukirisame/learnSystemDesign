# The Problem
- How do we maintain cluster information? - node-partition mapping, live nodes etc.
- How does nodes know the existence of other nodes in the cluster?
- How do nodes in a cluster communicate with each other?

# The Solution
1. Centralized state management service - like ZooKeeper => CP (consistent but a single point of coordination, can block on partition).
2. Peer-to-peer state management => AP (always available, eventually consistent)

# Centralized state management service
- So basically, Zookeeper keeps information of all the live nodes and parition information in its ephemeral nodes.
- Anyone who wants this information will place a watch on this cluster information znode to be notified about any change in parition and node.
- This provides high consistency.

# Peer-to-peer state management

Here, a node communicates with other nodes to share information. We have the following ways of transferring information from one node to another:
1. point-to-point broadcast
2. eager reliable broadcast
3. gossip protocol

## Point-to-point broadcast
<img width="500"  alt="image" src="https://github.com/user-attachments/assets/9d352c06-0628-475a-937d-064f6b864bf0" />

- The producer node (The node which has got something new to share), it sends a message directly to all the nodes in the cluster in a point-to-point broadcast fashion.
- If a consumer fails to get the information, then the producer will retry with that consumer.
- But if the producer also fails, then the new information is lost forever for that consumer. The consumer will never get it.

## Eager reliable broadcast
- The idea is this: Whenever a producer sends some information to consumers, the consumers will re-broadcast to every other node in the cluster.
- So lets suppose a producer sends a message to all the N consumers. The N consumers will then re-broadcast to all the other N nodes in the cluster.
- So, for every new information, we have O(n²) messages travelling through the network.
- Pros: It solves the problem with point-to-point broadcast: If the original producer fails, that's okay, the other nodes will broadcast that information. So for a failing consumer, N retries will be done.
- Cons: High network bandwidth due to O(n²) messages.

## Gossip Protocol
- The idea is this: A node which has received some new piece of information or periodically, it will transmit the information it has to a subset of other nodes in the cluster. The other nodes will then recursively pass on that information to other nodes in the cluster. Like spreading a rumor. **Eventually**, every node will get that information. 
- This approach takes about O(logN) time to spread a rumor, where N is the number of nodes in the cluster.
- With this approach, we have high availability of the information, but with eventual consistency.
- This approach is typically used for maintaining cluster information, to achieve consensus, and fault detection in distributed systems.

### Types of gossip protocol
- Anti-Entropy model
- Rumor-Spreading model

#### Anti-Entropy way
- Nodes periodically choose a random peer and compare their entire datasets/information to fix differences.
- Cons: Highly resource-intensive because you are checking all data. Systems use Merkle Trees (cryptographic hash trees) to quickly compare data ranges without sending the actual data over the wire.

#### Rumor-Spreading way
- When a node receives a new piece of data (a "rumor"), it actively chooses $K$ random nodes to forward that specific update to.


### Push vs Pull Model
- Push Model: The node with the latest message **sends** the message to a random subset of other nodes in the push model. This is efficient when we rarely get any new information or frequency of new information is less. Imagine a boring society where new events are rare. It would be wasteful of a person to keep asking for something new from other people. Rather, whenever something new happens, a person tells others.
- Pull Model: Every node will keep polling a random subset of nodes for any new messages. This is efficient when the frequency of new information is high. So, whenever a node polls other nodes, there is high chance of getting something new.
- Hybrid Approach: So basically during the initial phases of distributed systems, we tend to use push model, because initially we have less number of nodes or less information to share. When our system grows large and very happening (new nodes are added dynamically, removed dynamically, node failures), then its better to switch to pull model.


## Failure detection using gossip protocol

* Let's suppose we have four nodes in the cluster: **A, B, C, and D**.
* All the nodes periodically send **PING** messages to other nodes and expect **PONG** responses to verify that they are alive.
* Now, suppose **C crashes**.
* A sends a **PING** to C.
* A doesn't receive a **PONG** within the timeout period.
* A marks C as **PFAIL (Possibly Failed)**. This is only A's local suspicion. It does **not** declare C as dead immediately.
* Meanwhile, B and D also independently try to contact C as part of their normal health checks. They also fail to receive a response and independently mark C as **PFAIL**.
* At this point:

  * A thinks C is **PFAIL**.
  * B thinks C is **PFAIL**.
  * D thinks C is **PFAIL**.
* Through the **gossip protocol**, these nodes exchange their observations. Eventually, A, B, and D learn that the other master nodes also suspect C.
* Now, each node independently performs the same check:

  > "I think C is PFAIL, and a majority of the master nodes also think C is PFAIL. Therefore, C should be considered **FAIL**."
* As a result, A, B, and D all independently mark C as **FAIL**. No central coordinator is involved, and no node tells the others to declare C as failed. Every node reaches the same conclusion by applying the same algorithm to the same gossip information.

- The idea is this: Everyone is doing their independent checks, they are simply confirming by checking if everyone also thinks the same or not.


## New node discovery
The idea is simple. When a new node wants to join the cluster, it only needs to be introduced to one (or a few) existing nodes. Those nodes update their local cluster metadata and begin gossiping about the new node. As gossip messages continue to spread throughout the cluster, every node eventually learns about the new node and updates its own cluster metadata. In other words, the new node is introduced to a few nodes, and the gossip protocol spreads the "rumor" until the entire cluster becomes aware of it.
