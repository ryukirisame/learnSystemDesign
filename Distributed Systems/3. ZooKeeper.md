# ZooKeeper
- ZooKeeper is a **coordination service** for distributed systems.
- It acts as a source of truth for all the servers in a distributed system. It guarantees that everyone sees the same thing.

## What problem does it solve?
- **Leader Election**: If the current leader fails, who will be the next leader?
- **Service Discovery**: Which servers are currently alive and what are their addresses?
- **Configuration Management**: All the servers need to pick up a config change simultaneously
- **Distributed Locking**: Only server should process a job at a time
- **Cluster Membership**: Who is currently part of this cluster?

## Data Model of ZooKeeper
- ZooKeeper stores data in a heirarchical tree of nodes called **znodes** - just like filesystem.
- Every znode:
    - Has a unique path-like identifier.
    - Can store a small amount of data (upto 1MB)
    - Can have child znodes.
    - Has metadata (version numbers, timestamps, zxid etc)
- For example: `/cluster` is a znode
    -  It could contain data.
    -  And also have children.
- So, based on what we are doing with the znode, it could act as a directory or as a file.
- All the data is stored in-memory, for fast performance, and on disk also for durability. 
    - Here in ZooKeeper, the write is flushed to the Write-Ahead Log on disk first, and only after it is safely on disk is it written on memory. If it were written to memory first and the server lost power before flushing, consistency would be violated.
- 

### Types of ZNodes
1. Persistent ZNodes - persists until explicitly deleted. They are used for storing long-lived configuration or state.
2. Ephemeral ZNodes - Automatically deleted when the client that create it disconnects (stops sending heartbeat signals and zookeeper declares it dead). This znode is perfect for "Is this server alive?"
3. Sequential ZNodes - This is not a new type of ZNode, rather its basically either a Persistent/Ephemeral ZNode with an auto-incrementing number appended to their path by ZooKeeper.
    -  If three different backend workers simultaneously try to create a znode named `/queue/task-` and they enable the `SEQUENTIAL` flag, ZooKeeper will intercept the requests and create them in strict chronological order: `/queue/task-0000000001`, `/queue/task-0000000002`, `/queue/task-0000000003`. Even if those requests hit ZooKeeper at the exact same millisecond, ZooKeeper's internal consensus algorithm forces a total ordering. No two nodes will ever get the same sequence number.
    -  Useful for implementing Distributed Queues and Distributed Locks

#### Important thing about Ephemeral ZNodes
- Ephemeral znodes cannot have children. ZooKeeper doesn't allow that. 
- This is allowed:
```
/services                 (persistent)
    ├── payment-1         (ephemeral)
    ├── payment-2         (ephemeral)
    └── payment-3         (ephemeral)
```
- But this is not:
```
/services                 (persistent)
    └── payment-1         (ephemeral)
           ├── config
           └── metrics
```

 **But why does ZooKeeper doesn't allow this?**
 - If a node is ephemeral with children, what should zookeeper do with the children when the server of the ephemeral node crashes?
     - Delete the children as well?
     - Keep them?
     - Recursively delete?
- This complicates things. So ZooKeeper designers chose a simple rule: The ephemeral znode must be a leaf node. So that if the server disconnects, no recursive cleanup required.



## Watches
- Clients can set a watch on any znode. When that znode changes (data updated, node deleted, child added), ZooKeeper pushes a notification to the watcher.
- This is how distributed systems react to change without polling:
```
Server A watches /kafka/controller
  → Controller crashes → ZooKeeper deletes ephemeral node
  → Server A gets notified instantly
  → Server A triggers new leader election
```
- Please note: The watch is a one-time trigger. Once the znode changes and ZooKeeper notifies the concerned nodes, the nodes must place the watch again.

## ZooKeeper Ensemble Architecture
- ZooKeeper itself is distributed.
- It has a cluster of odd-numbered servers - usually 3,5,7 (for tie-breaking). This cluster in ZooKeeper has a special term - **Ensemble**.
- ZooKeeper is explicitly designed to be a CP system (Consistent and Partition Tolerant) under the CAP theorem. It prioritizes absolute correctness and total ordering of data over 100% availability.
    - Please mind that ZooKeeper provides availability through an ensemble of nodes, but if the majority of the nodes in ensemble are down, then only zookeeper goes down. Thats why it is not **100%** available.
- ZooKeeper follows the leader-follower architecture as well.
    - All the writes to zookeeper goes to the leader, which replicates to the followers. Because ZooKeeper provides **strong consistency**, a write request is a heavyweight operation and is only confirmed once a majority (quorum - `(N+1)/2`) acknowledges it.
    - Reads can be served by followers for performance, though follower reads may be slightly stale (we will come to this later).

- Majority of the servers must be available for ZooKeeper to work. For example: In an ensemble of `5` zookeeper servers, `(N+1)/2 = 3` must be alive.
- Because of this ensemble, ZooKeeper itself doesn't become a single point of failure.


# Cluster Membership using ZooKeeper
- In a distributed cluster, nodes come and go — they crash, restart, scale up, scale down. Every node needs an up-to-date answer to: "who else is alive right now?"
- Without this, a node might try to replicate data to a dead node, or a load balancer might route traffic to a server that no longer exists.

## How ZooKeeper Solves It
- Every node in the cluster, when it starts up, creates an ephemeral znode under a shared parent:
```
/db-cluster/members/
    ├── DB-1    → { address: "10.0.0.1", role: "leader",   joined: timestamp }
    ├── DB-2    → { address: "10.0.0.2", role: "follower", joined: timestamp }
    └── DB-3    → { address: "10.0.0.3", role: "follower", joined: timestamp }
```
- Every node watches `/db-cluster/members/` for children changes (add, remove, children added).

### When a node joins
```
DB-4 starts up
  ↓
Creates /db-cluster/members/DB-4 (ephemeral)
  ↓
ZooKeeper notifies all watchers: "new child added"
  ↓
All existing nodes will fetch the list and will learn about DB-4
  ↓
Leader starts replicating to DB-4
```

### When a node dies
```
DB-2 crashes
  ↓
ZooKeeper session times out
ZooKeeper deletes /db-cluster/members/DB-2 (ephemeral, auto-deleted)
  ↓
ZooKeeper notifies all watchers: "child deleted"
  ↓
All nodes fetches updated cluster list 
  ↓
Leader stops trying to replicate to DB-2
```
## Some Nuances
- Instead of every node watching `/db-cluster/members/`, we will have one dedicated routing layer, which will act as a source of truth for cluster membership. this routing layer will be the one that will watch `/db-cluster/members/`. When a node disconnects, zookeeper has to send the notification only to that one routing layer.


# Service Discovery using ZooKeeper
- In a microservices or distributed architecture, Service Discovery is the mechanism that allows services to find and talk to each other dynamically.
- Instead of hardcoding IP addresses (which change constantly as containers spin up, crash, or scale), services use a central registry. ZooKeeper is an excellent fit for this because it combines Ephemeral Nodes (for liveness tracking) and Watches (for instant updates).

## The ZooKeeper Service Discovery Architecture
The architecture consists of three main players:
- **The Provider (Service Instance)**: The microservice that wants to accept traffic (e.g., Payment Service).
- **The Registry (ZooKeeper)**: The source of truth holding the directory of IP addresses.
- **The Consumer (Client Service)**: The microservice that wants to call the provider (e.g., Order Service needs to talk to Payment Service).

## The Flow: Step-by-Step
### Step 1: Service Registration (Publishing)
When a new instance of the Payment Service boots up:
- It connects to the ZooKeeper ensemble.
- It creates an Ephemeral, Sequential ZNode under `/services/payment-service/instance_`.
- It stores its metadata (IP address, port, health status) inside that ZNode.

```
/services/
   ├── /payment-service/
   │      ├── instance_1  → { ip: "10.0.1.5", port: 8080, weight: 1 }
   │      └── instance_2  → { ip: "10.0.1.6", port: 8080, weight: 1 }
   └── /inventory-service/
          └── instance_1  → { ip: "10.0.2.1", port: 9000, weight: 2 }
```

### Step 2: Service Discovery (Locating)
When the Order Service needs to process a payment and needs an IP address:

- It queries ZooKeeper: "Give me all children under `/services/payment-service`."
- ZooKeeper returns the list of active IPs `(10.0.1.5, 10.0.1.6)`.
- The Order Service caches this list locally so it doesn't have to call ZooKeeper for every single API request. It then uses a load balancing algorithm (like Round Robin) to pick one of the IPs and calls it directly.


### Step 3: Staying Up to Date (The Watch)
When Order Service fetches the list of payment instances, it sets a Watch on the `/services/payment-service` parent ZNode.
- If a Payment node crashes: Its ZooKeeper session times out, and its Ephemeral ZNode is automatically deleted.
- If a new Payment node scales up: A new Ephemeral ZNode is created.

In either case, ZooKeeper instantly fires the Watch notification to the Order Service. The Order Service wakes up, fetches the freshly updated list of IPs, updates its local cache, and traffic flows smoothly without a single dropped request.

# Configuration Management using ZooKeeper
- Let's suppose we have N servers in our cluster, and there are some configurations that needs to be the same on all N servers. Since the configuration needs to be the same, so how do we propagate the configuration on all the N nodes? Some naive approach is:
    -  Manually do the configuration on all the N nodes. First of all, this approach is not scalabel at all. If we have 500 servers, we cannot do configuration on all of them. Secondly, there are chances of human error. Third, since the configuration is same for all, it makes more sense to have a centralised place where we keep the configurations and all the N servers simply use this.
    -  So the next best thing we can think of is a centralised config server. All the N servers will poll this config server to get the latest configs.
    -  But the problem with this is polling itself. Configuration is something that doesn't change frequently. So if the servers poll frequently, that's a wastage of network calls. Most of the time, the config server will respond with "Nothing new!". So most of the poll will be useless.
    -  If we decide to have a lower poll frequency, the servers will missing out on the latest config for a while if we actually have a config change.

- This is where ZooKeeper comes in. It allows us to propagate the latest config by instantly notifying the servers about the config change. Then the servers can pull the latest config themselves. 

## How zookeeper helps in config management

- Since configuration is something that has to persistent and is not tied to any node, so it makes sense to use Persistent ZNodes of ZooKeeper instead of the Ephemeral ZNodes.

```
/config/
   ├── /database/
   │      ├── url       → "jdbc:mysql://10.0.0.5:3306/db"
   │      └── timeout   → "500"  (Changed from 200)
   └── /feature-flags/
          └── new-ui    → "false"
```
### The flow
1. Node starts up, and fetches the configuration from ZooKeeper.
2. The node caches the fetched config and places a watch on `/config` persistent znode.
3. When Admin does any config value changes under `/config` znode, the watch fires up and notifies all the concerned nodes **simulataneously** - not sequentially.
4. The nodes then pulls the latest configuration from Zookeeper, caches it, and places the watch on `/config` znode AGAIN - because watches are one-shot thing, once used up, they expire.
5. Hot Reload: Now that the nodes have latest configuration, they can use that latest config without restarting the node.
    - This is called hot reload - config changes **take effect** on live running nodes without any downtime. 



# Leader-Election using ZooKeeper
- First of all, ZooKeeper doesn't do leader election, it _enables it_.
- The logic for leader election lives in application nodes themselves.

**Election Patterns**
## Pattern 1: Simple Race (FCFS)

### **How it works:**
- **The Race**: All 5 nodes simultaneously try to create a single, predetermined Ephemeral ZNode called `/election/leader`.
- **The Winner**: ZooKeeper guarantees that only one node can succeed in creating that exact path. The node that succeeds becomes the Leader.
- **The Losers**: The other 4 nodes receive a "Node Already Exists" error. They realize they lost, so they become Followers.
- **The Watch**: The followers immediately set a Watch on the /election/leader node and go to sleep.

### **The Failure Scenario:**
- If the Leader node crashes or loses network connectivity, its session with ZooKeeper times out. Because the ZNode was Ephemeral, ZooKeeper automatically deletes `/election/leader`.
- The Watch fires and alerts all 4 followers. They all wake up and race to create `/election/leader` again. A new winner emerges, and the cycle repeats.

### **Problem with this approach: Thundering Herd**
What happens if we have 1,000 nodes instead of 5?
- If the leader dies, all 1,000 followers are notified at the exact same time. They will all flood the ZooKeeper cluster with write requests to create the node. Only one wins, and 999 fail. This massive, sudden spike in network traffic and CPU utilization is called The Herd Effect (or Thundering Herd).

## Pattern 2: Sequential Znodes
- ZooKeeper supports sequential znodes — when you create one, ZooKeeper automatically appends a monotonically increasing number to it.

### **How it works:**
- When the system starts, every node that joins the election creates an **Ephemeral Sequential** ZNode under a parent directory, for example: `/election/guid-n_`.
- ZooKeeper automatically appends a sequential number to each. You end up with:
```
/election/guid-n_0001  ← Node A (LEADER)
/election/guid-n_0002  ← Node B (watches 0001)
/election/guid-n_0003  ← Node C (watches 0002)
/election/guid-n_0004  ← Node D (watches 0003)
```
- Each node then fetches the list of all children under `/election/`. The node with the lowest sequence number is the Leader. (In this case, Node A).

### **Avoiding the Herd Effect:**
This is where the magic happens. The nodes that don't have the lowest number (the followers) do not watch the leader. Instead, each node only watches the node right before it in line.
- Node B watches Node A (...0000000001)
- Node C watches Node B (...0000000002)


### **The failure scenario**

- If the Leader (Node A) crashes, its ephemeral node ...0000000001 vanishes.
- Because Node B was the only node watching Node A, only Node B gets notified. Node B wakes up, checks the directory, sees it now holds the lowest sequence number, and gracefully becomes the new Leader. Node C is completely undisturbed.
- Network traffic is $O(1)$ instead of $O(N)$ when a failure happens.

### A nightmare scenario with this approach
Imagine we have two nodes, Node A and Node B.
- Node A wins the election in ZooKeeper. It is now the official Leader.
- Everything was going well, but suddenly, Node A was hit by a massive JVM Garbage Collection (GC) pause. Its entire operating system freezes for 30 seconds.
- While Node A is frozen, its heartbeat session with ZooKeeper times out. ZooKeeper says, "Node A must be dead," deletes Node A's ephemeral node, and elects Node B as the new Leader.
- Then, Node B wakes up, and still thinks its the leader and might try to write data to the database. This is dangerous. In a system that was supposed to have a single leader now have two nodes who think they are the leader. Each leader will now independly accept writes. 
- This scenario is called "Split-Brain".

#### Solution of Split-Brain: Fencing Tokens
- Every time leadership changes, the new leader is issued a monotonically increasing number — a token.
- In ZooKeeper this is naturally available. Whenever a znode is created, it has something called `zxid`/`version number`, which always increases monotonically. We can use this as a fencing token.
- For fencing tokens to work, the resource being protected (database, storage layer etc), has to participate. The database/storage layer remembers the highest token it has ever seen.

#### How it works
```
[Node A: Token 1] --------> Attempts Write -------> [ Database ] (Remembers Max Token: 1)
                                                       | (Accepted)
                                                       v
  ... Node A freezes. ZooKeeper elects Node B ...
                                                       
[Node B: Token 2] --------> Attempts Write -------> [ Database ] (Updates Max Token to 2)
                                                       | (Accepted)
                                                       v
  ... Node A wakes up from freeze and tries to finish its old write ...
                                                       
[Node A: Token 1] --------> Late Write -----------> [ Database ] (Sees Token 1 < Max Token 2)
                                                       |
                                                       X REJECTED! (Fenced off)
```

Because the database already accepted a request with Token 2, it looks at Node A's request with Token 1 and says: "Nope. You are from the past. Request rejected." Node A has been safely "fenced" from causing damage.

**The key principle**: the resource being protected (the database, the storage layer, the file) must actively check and reject stale tokens. Leader election alone is not enough — the downstream resource has to participate in fencing.


## Pattern 3: Application-specific criteria
- Sometimes the new leader should be the one who has the up-to-date data.

Leader election in a distributed system has two completely separate concerns:

| Who | Job |
|---|---|
| **Application Code** | Decides *who should* become leader (the smart decision) |
| **ZooKeeper** | Guarantees *only one node can* claim leadership (the safe enforcement) |

- Neither can do the other's job. Both are essential.


3 database nodes. 1 leader, 2 followers. ZooKeeper running separately, watching all three.

```
         Clients
            │
      ┌─────▼──────┐
      │   Leader   │  ← DB-1  (10.0.0.1)
      │  (writes)  │
      └─────┬──────┘
            │ replication
      ┌─────┴──────┐
      │            │
┌─────▼─────┐ ┌────▼──────┐
│ Follower  │ │ Follower  │
│   DB-2    │ │   DB-3    │
│  (reads)  │ │  (reads)  │
└───────────┘ └───────────┘

ZooKeeper (separate cluster, always running)
/db-cluster/leader       → "DB-1 at 10.0.0.1"  (ephemeral)
/db-cluster/followers/2  → "DB-2 at 10.0.0.2"  (ephemeral)
/db-cluster/followers/3  → "DB-3 at 10.0.0.3"  (ephemeral)
```

All znodes are **ephemeral** — they auto-delete when the node that created them disconnects.

DB-2 and DB-3 are both **watching** `/db-cluster/leader` via ZooKeeper watches.



### Steady State (Before Any Failure)

#### Writes
- All writes go to **DB-1 (Leader) only**
- Leader writes to its own disk, then replicates to DB-2 and DB-3
- Only confirmed to the client **after followers acknowledge**

```
Client → DB-1 → replicates → DB-2 ✓
                           → DB-3 ✓
       ← "write confirmed"
```

#### Reads
- Reads can go to **any node** (leader or followers)
- Spreads read load across all three nodes

#### Replication Offset
As DB-1 processes writes, it keeps a counter called the **replication offset**.

```
DB-1 processes write #1000
  → DB-2 replicates it → offset: 1000
  → DB-3 replicates it → offset: 1000

All three are in sync.
```

DB-2 and DB-3 may not always be perfectly in sync — a follower that is slightly behind has a **lower offset** than the leader.


### The Failure

DB-1 crashes (power failure, hardware fault, etc.)

#### Step 1 — ZooKeeper Detects the Failure

```
DB-1 crashes
  ↓
DB-1's heartbeat to ZooKeeper stops
  ↓
ZooKeeper session times out (~3-5 seconds)
  ↓
ZooKeeper automatically deletes /db-cluster/leader  (ephemeral node gone)
```

ZooKeeper's job here: **passive detection via session timeout**. It doesn't ping DB-1 or investigate. It simply notices the heartbeat stopped and cleans up the ephemeral node.

#### Step 2 — Followers Are Notified

```
DB-2 was watching /db-cluster/leader
DB-3 was watching /db-cluster/leader
  ↓
Both get a watch notification instantly:
"The leader znode has been deleted"
```

No polling. No delay. ZooKeeper pushes this notification to all watchers the moment the node is deleted.



### The Election (Two Phases)

#### Phase 1 — Application Code Runs the Decision

This entire phase happens **inside the application code of DB-2 and DB-3**. ZooKeeper is not involved here.

**Step 3 — Followers check their replication offsets**

```
DB-2: "I have replicated up to offset 1000"
DB-3: "I have replicated up to offset 997"
```

DB-3 fell 3 writes behind before DB-1 crashed. This is normal — replication has a tiny lag.

**Step 4 — Followers broadcast offsets to each other**

DB-2 and DB-3 communicate directly (not through ZooKeeper):

```
DB-2 → DB-3: "My offset is 1000"
DB-3 → DB-2: "My offset is 997"
```

**Step 5 — Each node independently runs the election algorithm**

The rule baked into the application code:

> *"The node with the highest replication offset should be the new leader.  
> That node has the most complete data and minimizes data loss."*

Both DB-2 and DB-3 run this same logic independently:

```
DB-2 runs algorithm:
  Alive nodes   = [DB-2 (1000), DB-3 (997)]
  Highest offset = DB-2
  Decision: "I should be the leader. I will try to claim it."

DB-3 runs algorithm:
  Alive nodes   = [DB-2 (1000), DB-3 (997)]
  Highest offset = DB-2
  Decision: "DB-2 should be the leader. I will step back."
```

DB-3 steps back voluntarily. It doesn't even try to claim leadership.

> **This decision logic — "highest offset wins" — is Java/Go/Python code inside the database application. ZooKeeper has no idea this rule exists.**



#### Phase 2 — ZooKeeper Enforces the Claim

Even though DB-3 stepped back gracefully in Phase 1, there are scenarios where both nodes might try to claim leadership simultaneously (network partition, race condition, bugs). ZooKeeper's job is to make the claim **safe and atomic** regardless.

**Step 6 — DB-2 claims leadership in ZooKeeper**

```
DB-2 creates /db-cluster/leader znode
  with value: "DB-2 at 10.0.0.2"
  ↓
ZooKeeper atomically creates it
  ↓
DB-2 is officially the new leader
```

If DB-3 had also tried simultaneously:

```
DB-2 and DB-3 both try to create /db-cluster/leader
  ↓
ZooKeeper processes writes sequentially — one at a time
  ↓
DB-2 arrives first → node created ✓
DB-3 arrives second → "node already exists" error ✗
  ↓
DB-3 accepts it → becomes follower under DB-2
```

**This is ZooKeeper's core guarantee: exactly one node wins, no matter what.**



### After Election

**Step 7 — Cluster reconfigures**

```
ZooKeeper now looks like:
  /db-cluster/leader       → "DB-2 at 10.0.0.2"  (ephemeral)
  /db-cluster/followers/3  → "DB-3 at 10.0.0.3"  (ephemeral)

DB-3 updates its replication source:
  Before: "replicate from DB-1"
  After:  "replicate from DB-2"

Clients check ZooKeeper for the current leader:
  Before: "send writes to DB-1"
  After:  "send writes to DB-2"
```

**Step 8 — Normal operation resumes**

```
DB-2 is now leader — accepts all writes
DB-3 is follower  — serves reads, replicates from DB-2
Cluster is healthy again (with 1 less node until DB-1 recovers)
```



### The Full Flow — All Steps Together

```
DB-1 crashes
    │
    ▼
ZooKeeper session times out
ZooKeeper deletes /db-cluster/leader      ← ZooKeeper (detection)
    │
    ▼
Watch notification fires to DB-2 and DB-3 ← ZooKeeper (notification)
    │
    ▼
DB-2 and DB-3 exchange replication offsets ← Application code
    │
    ▼
Each node runs "highest offset wins" rule  ← Application code (the decision)
DB-3 steps back. DB-2 moves forward.
    │
    ▼
DB-2 creates /db-cluster/leader in ZK     ← ZooKeeper (atomic enforcement)
Only one node can succeed — DB-2 wins
    │
    ▼
DB-3 updates replication source to DB-2   ← Application code
Clients redirect writes to DB-2           ← Application code / load balancer
    │
    ▼
Cluster resumes normally
```


### Why Two Phases Are Necessary

| Scenario | What happens without ZooKeeper enforcement |
|---|---|
| Network partition during Phase 1 | DB-2 and DB-3 can't talk to each other. Both think they should be leader. **Split-brain** — two leaders accepting conflicting writes. Data corruption. |
| Bug in application logic | Both nodes decide they should win. Without atomic enforcement, both become leaders. |
| Race condition | Phase 1 completes correctly but both nodes race to claim leadership at the same millisecond. |

ZooKeeper's atomic write is the **safety net** for all these cases. Even if the application logic is perfect, the enforcement layer ensures correctness under all failure scenarios.






# Building Distributed Lock using ZooKeeper


Let's look at how sequential znodes solve a classic system design interview question: **"How do you ensure only one worker processes a sensitive task at a time?"**

Suppose we have 3 workers (`Worker-A`, `Worker-B`, `Worker-C`) trying to grab a lock called `/resource-lock`.

### Step 1: Enqueueing via Ephemeral Sequential Nodes

Each worker creates an **Ephemeral Sequential** znode under the `/resource-lock` path, appending its own identifier to the name.

ZooKeeper generates the following tree:

* `/resource-lock/lock-0000000001` (Created by Worker-B)
* `/resource-lock/lock-0000000002` (Created by Worker-A)
* `/resource-lock/lock-0000000003` (Created by Worker-C)

### Step 2: Determining the Winner

After creating its node, every worker fetches the list of all children under `/resource-lock`.

* **Worker-B** sees it owns `lock-0000000001`. Since it has the **lowest number**, Worker-B successfully acquires the lock and starts processing the resource.

### Step 3: Efficient Waiting via Watches

The remaining workers realize they didn't win, so they must wait. To avoid overloading ZooKeeper, they don't poll. Instead, they form a fair chain:

* **Worker-A** (`0000000002`) places a **Watch** on the node right in front of it: `lock-0000000001`.
* **Worker-C** (`0000000003`) places a **Watch** on the node right in front of it: `lock-0000000002`.

### Step 4: Releasing and Handing Off

When Worker-B finishes its job (or if it crashes, causing its ephemeral session to disconnect), its znode `lock-0000000001` is deleted.

* ZooKeeper instantly fires a notification to **Worker-A** (because it was watching `0000000001`).
* Worker-A wakes up, checks the directory, confirms it now holds the lowest remaining number, and safely takes over the lock.
