# Data Partitioning
- If our dataset becomes so large that it cannot be contained in a single node, then we must partition the data among different nodes.
- In a distributed system, partitioning (also called sharding) is the process of splitting a large dataset across multiple nodes so that each node holds only a subset of the data.
- The main reason for wanting to partition data is scalability. By distributing data across multiple nodes, the query load spreads across multiple nodes.
- Queries that involve just one partition, the node containing it can handle it alone. But, if there's a query that requires different partitions, all the nodes involved must be queried in parallel. This is called `Scatter-Gather` problem.
- Partitioning is usually combined with replication, so that copies of each partition are stored on multiple nodes.
- A node may store more than one partition. If a leader-follower replication model is used, the combination of partitioning & replication will look something like this:
<img width="800"  alt="image" src="https://github.com/user-attachments/assets/ad05afae-cda6-4125-8f7c-cf0000ac910b" />

- In this image, our dataset is split into 4 partitions/shards among 4 nodes with **replication factor** of 3.
- So, each shard has 3 copies distributed among 4 nodes. For example: shard 1 is present in node 1, node 3 and node 4.
- Among those 3 copies, there is one leader. for shard 1, the leader lives in node 1.
- When client wants to write data that belongs to partition 1, the request will go to node 1, because that is where leader of partition 1 lives.

## Why a node can contain multiple partitions
If we allowed just one partition per node, then it would suffer from a major flaw. 
- **The "Stranded Capacity" Problem**: Imagine Node A has a 2 Terabyte hard drive. You assign it Partition 1. If Partition 1 only grows to 10 Gigabytes and then stops, 99% of Node A's expensive disk space and CPU power goes completely wasted. By allowing multiple partitions per node, the database can pack Partition 5, Partition 12, and Partition 48 onto that same node to fully utilize the hardware.

# Problem with partioning
- The goal with partitioning is to spread the data and the query load evenly across nodes.
- If the partitioning is un-even/unfair, so that some partitions have more data or queries than others, we call it **skewed**. This makes partitioning much less effective.
- Imagine a scenario in which all load ends up on one partition, so 9 out of 10 nodes are idle and your bottleneck is the single busy node.
- A partition with disproportionately high load is called **hot spot**.
- This hotspot is what we want to reduce.
- We do this by having a good partitioning strategy so the data and query gets uniformly distributed among nodes.

# Core Partitioning Strategies

## 1. Random Partitioning
- Not really a strategy, but worth mentioning this approach.
- This is the simplest approach. Assign a random node for each data.
- This would distribute data quite evenly across the nodes.
- But the problem is, when we're trying to read a particular item, we don't know which node it belongs to. So we will have query all nodes in paralle.

## 2. Range Partitioning
- The dataset is divided into **contiguous ranges of keys**, and each partition owns one range. 
- The system establishes boundaries (boundaries can be alphabetical, numerical, or chronological) so that it knows exactly which partition holds a specific key without checking anywhere else.

### Real-World Example: An E-Commerce Analytics System
- Imagine we are building an application that tracks millions of user transactions. We decide to use Transaction ID as the partition key to partition our data. 
- Let's assume our data is partitioned across 4 logical partitions (P1, P2, P3, P4) distributed across your cluster:
```
P1 -> 1 to 250000
P2 -> 250001 to 500000
P3 -> 500001 to 750000
P4 -> 750001 to 1000000
```

#### Scenario A: A Single-Key Lookup (Point Query)
- Query: `SELECT * FROM tx_table WHERE tx_id = 612450;`
- How the system handles it: The routing layer(e.g., Apache ZooKeeper or a centralized coordinator) checks the metadata table. It sees that 612450 falls squarely between 500001 and 750000 (P3).
- Performance: The query is routed directly to the node hosting P3. The other three nodes never even know the query happened. This is highly efficient.

#### Scenario B: A Sequential Search (Range Query)
- Query: `SELECT * FROM tx_table WHERE tx_id BETWEEN 300000 AND 400000;`
- How the system handles it: The database looks at the ranges and recognizes that the entire requested dataset resides entirely within P2.
- Performance: It performs a fast, sequential disk scan on the single node holding P2. This avoids the expensive `Scatter-Gather` problem entirely.

### Problem with Range Partitioning
- If our application uses an auto-incrementing ID or a timestamp as the partition key, think about how writes arrive:
  - Transaction 1000001 comes in -> Belongs to the new highest range (e.g., P5).
  - Transaction 1000002 comes in -> Belongs to P5.
  - Transaction 1000003 comes in -> Belongs to P5. 
- Since keys are being auto-incremented, all the new writes will go to P5. The write operation is totally skewed towards node that contains P5, while other nodes sit idle.

### Fixing the problem: Compound Partition Keys
- Instead of partitioning purely by `timestamp` or `tx_id`, we partition using a compound key: (merchant_id, transaction_timestamp).
- How data distributes now:
  - Data is partitioned across physical nodes using the Partition Key (merchant_id). Within that node, data is stored in sorted chronological order using the Clustering/Sort Key (transaction_timestamp).
  
```
P1 (Node A) -> Handles Merchant IDs: A to F
P2 (Node B) -> Handles Merchant IDs: G to M
P3 (Node C) -> Handles Merchant IDs: N to S
P4 (Node D) -> Handles Merchant IDs: T to Z
```
- During a high-traffic sales event, concurrent transactions are scattered naturally across the cluster by merchant.
- A purchase at Apple (merchant_id: Apple) routes to P1 (Node A).
- A purchase at Nike (merchant_id: Nike) routes to P3 (Node C).
- A purchase at Walmart (merchant_id: Walmart) routes to P4 (Node D).


#### Query 1
- "Give me all transactions for Nike between 12:00 AM and 1:00 AM."
- The database looks at the first part of the key (Nike), knows instantly it lives on P3 (Node C), goes to that single node, and performs a blazing-fast sequential scan because the data inside Node C is already pre-sorted by transaction_timestamp.

#### Query 2
- "Give me ALL transactions globally across the entire platform between 12:00 AM and 12:05 AM."
  - Because the data is partitioned by merchant_id, transactions from 12:00 AM to 12:05 AM are now scattered across Node A, Node B, Node C, and Node D.
  - The system must execute a Scatter-Gather query, asking every single node for its data from that time frame, and then merge the results.

### Interview Takeaway
If an interviewer asks you to design a system with heavy sequential writes (like IoT sensor data or financial logs) but requires range queries, proposing a Compound Key shows you understand how to protect your nodes from hot-spotting while maintaining localized query efficiency.


## 3. Hash Partitioning
- Instead of using the key directly, you pass it through a hash function and use the output to assign it to a partition. A simple version looks like: `partition = hash(key) % number_of_partitions`
- So, even though the keys are sequential, the data is scattered perfectly and evenly across the entire cluster.

### Advantages
Evenly distributes data across nodes, effectively destroying hotspots caused by sequential data (like auto-incrementing IDs or timestamps) that we faced in range partitioning.

### Disadvantages
- A **range query** like "give me all orders from the last 7 days" can no longer be answered by scanning one or two partitions, you'd have to query all partitions and merge the results. This is called a **scatter-gather query** and is expensive.
- Also, the naive `hash % N` approach has a serious flaw: if you add or remove a node, `N` changes, and nearly every key maps to a different partition, forcing a massive data reshuffle. To deal with this, we have something called **Consistent Hashing**.
- Consistent Hashing is not a partitioning strategy, rather a way to deal with key reshuffling if we add/remove nodes in the cluster.


# Celebrity Problem
- The infamous "Justin Beiber" problem. Since JB is popular and he has millions of followers in instagram, his account gets lots of reads and write operations (likes, comments etc).
- If we partition our dataset using user_id, then one of the partitions will end up with JB's data. And since JB gets high traffic, the node containing that partition will get overwhelmed.
- Most of the users on instagram don't have much traffic. They are fine. But for exceptional accounts like JB, its partition becomes skewed.
- This isn't just a social media problem. The same pattern appears in:
  - E-commerce — a viral product on a flash sale day
  - News platforms — a breaking story being read by millions simultaneously
  - Financial systems — a heavily traded stock symbol
  - Gaming — a shared resource or leaderboard entry contested by many players

## Why Hash Partitioning Fails Here
- When JB posts something, a **single write request** hits their designated partition key. However, millions of users instantly query that exact same user_id partition to read the post or append a comment.
- Because all traffic for that specific ID hashes to the exact same partition ID, a single node gets entirely crushed by read/write concurrency, regardless of how many hundreds of idle nodes exist in the cluster.

## Solutions
### 1. Key Splitting / Salting
- The most direct approach is to artificially split the hot key into multiple sub-keys by appending a random suffix (called a salt). Instead of writing all data under celebrity_123, you write to celebrity_123_0, celebrity_123_1, ..., celebrity_123_N. Because these are now different keys, the hash function sends them to different partitions, spreading the load.
- This spreads the write operation across multiple partitions.
- But for reads, we now have to read from all sub-keys and merge the results in the application layer. This is the trade-off with salting.
- Best For: Write-heavy hot spots.

### 2. Caching
- For read-heavy hot-keys, we can use caching.
- For example: Millions of people reading JB's post
- We can use **distributed cache layer** - Redis/Memcached. Distributed because we don't want the cache layer to crash as well.
- The first request for a celebrity's data fetches it from the database and stores it in the cache. Subsequent requests are served directly from cache, never reaching the database partition at all.
- Best for: Read-heavy hot spots where data doesn't change too frequently.

### 3. Follower Replicas
- For read-dominated hot spots, you can create multiple replicas of the hot partition and distribute read traffic across them using a load balancer or round-robin routing. Writes still go to the primary, but reads are spread across N replicas, multiplying your read throughput by N.
- The trade-off is replication lag. Replicas may serve slightly stale data. For a celebrity's follower count or like count, this is usually acceptable. For financial transactions, it is not.
- Best for: Read-heavy hot spots where eventual consistency is acceptable.

### 4. Application level push vs pull model
- This is an architectural solution used by large social media platforms, and it addresses the celebrity problem at the data model level rather than the storage level.
- There are two naive approaches to building a social media feed:
  -  Push model (fan-out on write): When a user posts, the system immediately writes a reference to that post to the feed of every follower. Reads are cheap, your feed is precomputed. But for a celebrity with 50M followers, a single post triggers 50M writes. This is the fan-out hot spot problem. So when JB posts something, that post is written to the feed of every single follower of his.
  -  Pull model (fan-out on read): When you open your feed, the system queries the accounts you follow and builds your feed on the fly. Writes are cheap — just one write per post. But reads are expensive, especially for users who follow many people.
- A hybrid model:
  - This is what Twitter/X, Instagram, and similar platforms actually do. They use the push model for regular users (fast feed reads) and the pull model specifically for celebrities. Celebrity posts are not pre-pushed to all followers. Instead, when you load your feed, the system assembles it by merging your precomputed feed with a real-time pull of any celebrity accounts you follow.
  - So basically when I post something on instagram, since i am a regular user and don't have many followers, my post will be written to the feed of every single follower of mine (lets say ~50).
  - Now, when my friend opens his instagram, my post will be pre-populated in his feed. As for the celebrity he follows, pull-model will be used for that celebrity to get the latest post from that celebrity. 

# Primary & Secondary Indexes
- Till now we have partitioned our data using the primary key.
- Lookups by primary key was straightfoward - the routing layer will hash or range the key to find the right partition immediately.
- But what if we want to query not by primary key, but some other field?
- For example, imagine you have a database of cars partitioned by car_id. You want to query all red cars, or all cars made by Toyota. Neither color nor make is your partition key, so there's no direct way to know which partition holds the data you want. That's exactly the problem secondary indexes solve.
- There are two main approaches to partitioning a database with secondary indexes: Local Secondary Indexes and Global Secondary Indexes

## Local Secondary Indexes (Document-Based Partitioning)
- Each partition maintains its own independent secondary index of the data it holds. The index is local - it knows nothing about what's in other partitions.

### How it works
<img width="800"  alt="image" src="https://github.com/user-attachments/assets/5e707aa8-6c61-4603-9d1b-47d37b269836" />

- When you write a car with color = red to partition 0, partition 0 updates its local index to record that this car is red. The index entry only points to cars within partition 0. Partition 1 has its own separate index entry for color = red pointing only to its own red cars.
- **Writes are simple and fast**. When you write to a partition, you only update that partition's local index.
- **Reads require a scatter-gather query**. To find all red cars across the entire database, you have to send the query to every single partition, ask each one to consult its local index, collect all the results, and merge them in the application layer. This is called a scatter-gather or fan-out read.

## Global Secondary Indexes (Term-Based Indexing)
- We build a single global index that covers all data across all partitions. But since a single index on a single node would become a bottleneck, the global index is itself partitioned — just differently from the primary data.
- The global index is partitioned using the second index field itself (in this case, the color = 'Red'). So basically the idea is this:
  - ```
    Index Partition 1 (colors A–M):
    color=blue  → [car_023 on P4, car_187 on P1, car_445 on P7]
    color=green → [car_091 on P2, car_302 on P5]

    Index Partition 2 (colors N–Z):
    color=red   → [car_101 on P1, car_389 on P2, car_512 on P3, car_780 on P3]
    ```
- **Reads are efficient**. To find all red cars, you go to index partition 2, look up color=red, and get back a list of exactly which primary data partitions hold red cars. You only need to contact those specific partitions, not all of them. This is much more targeted than scatter-gather.
- **Writes are more complex and slower**. When you add a new red car to a primary partition, you also need to update the global index partition that owns color=red. This means a single write now touches multiple partitions — the primary data partition and one or more index partitions.
- If we update the color of a car from blue to red, this single update requires:
  - Updating the primary data partition with the new value.
  - Removing the old entry from the global index partition owning color=blue.
  - Adding a new entry to the global index partition owning color=red.
  - These three operations touch three different partitions, potentially on three different nodes.
- For this reason, global index updates are asynchronous, meaning the index may lag behind the actual data by a short period.


# Rebalancing Partitions
- The process of moving partitions and data load from one physical node to another in a cluster is called **rebalancing partition**.
- When to perform partition rebalancing
  - When a new node is added in the cluster.
  - When an existing node fails.
  - When a node is gracefully removed from the cluster.
  - The data distribution becomes severely skewed (hotspots).

- **The Golden Rule**: Move the **absolute minimum amount of data** possible. Why? Because data movement is expensive in terms of network and disk I/O and especially on an enterprise scale.
- Also, during rebalancing, our system should be available - read and writes should continue working while data is being moved.

## Strategies for rebalancing

### How not to rebalance: `hash(key) % N`
- If your database uses the standard modulo operator against the number of nodes ($N$) to route data, scaling(adding/removing) becomes a disaster.
- Please refer to the problem that consistent hashing solves.

### Fixed number of partitions
- In this strategy, we create way more logical partitions than nodes on Day 1, and you never change that number. For example, you decide on exactly 1,000 logical partitions for a 10-node cluster (each node holds 100 partitions).
- Now, when a new node joins the cluster, the new node can steal a few partitions from every existing node until partitions are fairly distributed once again. If a node is removed from the cluster, the same happens in reverse.

<img width="800" alt="image" src="https://github.com/user-attachments/assets/ddbfb9d7-c1fb-4f78-a27c-1544b50b4936" />

- Only entire partitions are moved between nodes. The number of partitions does not change, nor does the assignment of keys to partitions. The only thing that changes is the assignment of partitions to nodes.
- Now, it takes some time to move partitions, so the old assignment of partitions is used for reads and writes that happen while the transfer is in progress, hence ensuring availability during rebalancing.
- Pros: Extremely simple.
- Cons: Choosing the right number of partitions is difficult if the total size of the dataset is highly variable (if it starts small but may grow much larger over time). Since the number of partitions are fixed, their size would grow over time. When the partitions become too large, rebalancing becomes expensive.
  - If we choose too many partitions, managing those tiny partitions would be difficult. If we choose choose too less partitions, size of each partition would grow too large over time. 
- The best performance is achieved when the size of the partitions is "just right", neither too large, nor too small, which can be hard to achieve.
  
### Dynamic Partitioning
- This strategy can be applied on both: key range-partitioned data, and hash-partitioned data both. 
- So the idea is, when a partition grows beyond a configured size threshold (say 10GB), it is automatically split into two roughly equal halves. Conversely, if a partition shrinks below a threshold due to deletions, it can be merged with a neighboring partition.
- After a large partition has been split, one of its two halves can be transferred to another node in order to balance the load.
- The advantage of dynamic partitioning is that the number of partitions adapts to the total size of the dataset.
- There is a problem with this approach:
  - When you start with an empty database, you have a single partition on a single node. All writes go to that one node while the others sit idle, until the partition grows large enough to split.
  -  To address this, systems like HBase support pre-splitting — you can configure an initial set of partitions at cluster creation time based on your expected key distribution.

### Consistent hashing with virtual nodes

- What is the problem we are trying to solve here? How to distribute keys/partitions among nodes such that each node handles equal amount of load.
  - Consitent hashing with virtual nodes solves exactly this problem.
