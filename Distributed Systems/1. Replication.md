
# Distributed Data Idea
There are various reasons why you might want to distribute a database across multiple machines:
- Scalability:  If your data volume, read load, or write load grows bigger than a single machine can handle, you can potentially spread the load across multiple machines.
- Fault tolerance/high availability: If your application needs to continue working even if one machine (or several machines, or the network, or an entire datacenter) goes down, you can use multiple machines to give you redundancy. When one fails, another one can take over.
- Latency: If you have users around the world, you might want to have servers at various locations worldwide so that each user can be served from a datacenter that is geographically close to them. That avoids the users having to wait for network packets to travel halfway around the world.

**Ways to distribute data:**
- Replication: Keeping a copy of the same data on several different nodes, potentially in different locations. Replication provides redundancy: if some nodes are unavailable, the data can still be served from the remaining nodes. Replication can also help improve performance.
- Partitioning: Splitting a big database into smaller subsets called partitions so that different partitions can be assigned to different nodes (also known as sharding).

Usually, both of them are used together. We will partition our data, and keep replicas of each partition as well.

# Replication
- Important Assumption: The dataset is very small such that it can fit entirely on one machine.
- Two scenarios:
  1. Dataset does not change: This is a simple case. We can simply copy the data to multiple machines/replicas once and we are done.
  2. Dataset changes over-time: This introduces the problem of syncing each replica. There are three algorithms that are used for replicating changes between nodes:
     - Single-Leader Replication
     - Multi-Leader Replication
     - Leaderless Replication

# Leaders & Followers / Master-Slave
- Whenever we write something to the database, it needs to be processed by every replica, to make sure all the replicas contain the same data.
- Leader-based replication is a common solution for this.

**How does it work**
- One of the nodes/replicas is appointed the leader/master/primary. Whenever client performs a write operation, it goes to the leader only and never to the replicas. The primary/leader then logs that write operation into a file called _replication log_. This log file (also called write-ahead log), is an ordered, append only record of every write operation that occurs on a primary/leader node. It's the source of truth for keeping replicas in sync. 
- The primary node writes every change to the log before applying it to the actual data store. Replica/follower nodes then consume this log and replay the same operations in the same order to stay consistent with the leader.
  - The replication log could be statement-based: logs raw SQL commands, or, Row-Based: logs the actual before/after values of rows changed.
- When the client wants to read from the database, it can query either the leader or any of the followers. However, write are only accepted by the leader.

## Synchronous Vs Asynchronous Replication
- Replication to the follower nodes could happen synchronously or asynchronously.

In the image, the replication to follower 1 is synchronous and replication to follower 2 is asynchronous.

### Synchronous Replication
- The leader waits until follower 1 has confirmed that it received the write. Then only the leader will proceed with notifying the client that the write was successful.
- Advantage is that it is guaranteed that the replica has the latest data. So, just in case, if the leader fails, the replica can serve.
- Disadvantage is that the leader must wait for the replica to confirm the write. So, latency is as good as the slowest replica. If the replics crashes, the leader must block new write operations and wait until the replica comes back online.
- For this reason, it is not wise for all replicas to be synchronous. If any one of the replicas crash, the entire system will come to halt.
- This is why fully synchronous replication across many replicas is rarely used in practice. Most systems that offer synchronous replication let you designate just **one** synchronous replica (semi-synchronous), with the rest being asynchronous. If the synchronous replica becomes unavailable or slow, one of the asynchronous followers is made synchronous. This guarantees that we have latest data on at least two nodes: the leader and one synchronous replica.  This configuration is called **semi-synchronous**.
