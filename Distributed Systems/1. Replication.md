
# Distributed Data Idea
There are various reasons why you might want to distribute a database across multiple machines:
- Scalability:  If your data volume, read load, or write load grows bigger than a single machine can handle, you can potentially spread the load across multiple machines.
- Fault tolerance/high availability: If your application needs to continue working even if one machine (or several machines, or the network, or an entire datacenter) goes down, you can use multiple machines to give you redundancy. When one fails, another one can take over.
- Latency: If you have users around the world, you might want to have servers at various locations worldwide so that each user can be served from a datacenter that is geographically close to them. That avoids the users having to wait for network packets to travel halfway around the world.

**Ways to distribute data:**
- Replication: Keeping a copy of the same data on several different nodes, potentially in different locations. Replication provides redundancy: if some nodes are unavailable, the data can still be served from the remaining nodes. Replication can also help improve performance.
- Partitioning: Splitting a big database into smaller subsets called partitions so that different partitions can be assigned to different nodes (also known as sharding).

Usually, both of them are used together. We will partition our data, and keep replicas of each partition as well.

# Replication
- Important Assumption: The dataset is very small such that it can fit entirely on one machine.
- Two scenarios:
  1. Dataset does not change: This is a simple case. We can simply copy the data to multiple machines/replicas once and we are done.
  2. Dataset changes over-time: This introduces the problem of syncing each replica. There are three algorithms that are used for replicating changes between nodes:
     - Single-Leader Replication
     - Multi-Leader Replication
     - Leaderless Replication

# Leaders & Followers / Master-Slave
- Whenever we write something to the database, it needs to be processed by every replica, to make sure all the replicas contain the same data.
- Leader-based replication is a common solution for this.

**How does it work**
- One of the nodes/replicas is appointed the leader/master/primary. Whenever client performs a write operation, it goes to the leader only and never to the replicas. The primary/leader then logs that write operation into a file called _replication log_. This log file (also called write-ahead log), is an ordered, append only record of every write operation that occurs on a primary/leader node. It's the source of truth for keeping replicas in sync. 
- The primary node writes every change to the log before applying it to the actual data store. Replica/follower nodes then consume this log and replay the same operations in the same order to stay consistent with the leader.
  - The replication log could be statement-based: logs raw SQL commands, or, Row-Based: logs the actual before/after values of rows changed.
- When the client wants to read from the database, it can query either the leader or any of the followers. However, write are only accepted by the leader.

## Synchronous Vs Asynchronous Replication
- Replication to the follower nodes could happen synchronously or asynchronously.

<img width="800"  alt="image" src="https://github.com/user-attachments/assets/0933b95a-a1e2-4242-8b7d-f3def6ae4870" />

In the image, the replication to follower 1 is synchronous and replication to follower 2 is asynchronous.

### Synchronous Replication
- The leader waits until follower 1 has confirmed that it received the write. Then only the leader will proceed with notifying the client that the write was successful.
- Advantage is that it is guaranteed that the replica has the latest data. So, just in case, if the leader fails, the replica can serve.
- Disadvantage is that the leader must wait for the replica to confirm the write. So, latency is as good as the slowest replica. If the replics crashes, the leader must block new write operations and wait until the replica comes back online.
- For this reason, it is not wise for all replicas to be synchronous. If any one of the replicas crash, the entire system will come to halt.
- This is why fully synchronous replication across many replicas is rarely used in practice. Most systems that offer synchronous replication let you designate just **one** synchronous replica (semi-synchronous), with the rest being asynchronous. If the synchronous replica becomes unavailable or slow, one of the asynchronous followers is made synchronous. This guarantees that we have latest data on at least two nodes: the leader and one synchronous replica.  This configuration is called **semi-synchronous**.

### Asynchronous Replication
- The leader writes locally, acknowledges the client immediately, and then propagates the change to replicas in the background. The client doesn't wait for replicas to confirm anything.
- The benefit is low latency to client and high availability of write operations. The leader can keep accepting writes even if replicas are lagging or temporarily offline.
- Cons: Replication lag. There's a window of time where replicas are behind the leader. If the leader crashes during that window, any writes that hadn't yet been shipped to replicas are lost — this is called replication lag causing data loss, and the gap is sometimes called the replication lag window.

## Setting up new followers
If we add a new node, how do we make sure the node is up-to-date with the leadeer?

### Naive Approach
- Just copy the data from leader to the new node.
- Problem with this approach is that the leader keeps accepting new writes frequently. By the time data copy finishes, the leader already has new data and our data in new node is stale. We also don't have the option of locking the leader for new writes, that would kill availability.

### Better Approach
- We can use RDB(dump file) + AOF(replication log) approach.
- We take snapshot of leader's data at fixed intervals/ at some point in time. This snapshot must correspond to a log number in replication log, which is called a log sequence number or binlog coordinates. The idea is - if the snapshot was taken then it should correspond to a log number (lets say 48) in the replication log.
- We copy that snapshot to the new node. Meanwhile, the leader keeps accepting new writes and keep logging it to replication log.
- Once the copy is finished, the new node takes the replication log and starts from the log number from where new data came. In our case, it will start replaying log from log number 49.
- Once the log replay is done, the node will eventually catch up with the leader. 

## Handling Node Outages
### Follower Failure
- This is the simple case. Each follower knows the last log position it processed. Once it comes back online, it can request the leader to give it the new logs after that last known position. Then it replays the latest logs and eventually it catches up with the leader.
- Another brute force approach would be to use the leader snapshot + replication log, if the node wants to start fresh.

### Leader Failure (failover)
- This one is a hard problem to solve.
- When the leader goes down, one of the followers needs to be promoted to become the new leader, and the rest of the system needs to be reconfigured to send writes to it. This process is called failover.
- Failover can happen either manually, where the admin is notified that the leader has failed, and then the admin takes necessary steps to make a new leader. Or, it could happen automatically.
- How does automatic failover detects that the leader is down?
  - A typical approach would be a timeout: if the leader doesn't respond in lets say 30 sec, the system considers it to be down.
- How does automatic failover choose a new leader?
  - This is typically done by an election process among the remaining followers. The node with the most up-to-date replication log from the old leader is chosen to be the new leader to minimize data loss. In ideal situation, the new follower should have all the data from previous leader.
- Now that we have a new leader, we configure the system to use the new leader. So now the clients would ask the new leader for write operations.

#### Problems with failover
- If replication was asynchronous and the old leader had accepted writes that hadn't been replicated yet, those writes are gone when the new leader takes over. Some systems handle this by having the new leader simply discard those writes, which can cause inconsistencies if the client received a success acknowledgment for them.
- The Split-Brain problem: If the old leader comes back online and doesn't realize it's been demoted, you now have two nodes both acting as leader and accepting writes independently. This is one of the most dangerous failure modes in distributed systems because both leaders are diverging silently.
  - A solution would be to tell the old leader (when it comes back online) that it has been demoted. Or, prevent it from accepting any new writes - called fencing. 
  - If the system detects that we have two leaders, there should be a mechanism to shut one of them down. 

#### A case study
- In one incident at GitHub, an out-of-date MySQL follower was promoted to be the leader. The follower replication was asynchronous.
- The MySQL DB was using auto-increment counter for ID. And the new leader's autoincrement counter was behind the old leader.
- Now, since the new leader came, it started issuing primary keys IDs that the old leader had already used for different records.
- Now, before the old leader crashed, the records were cached in Redis. Now, since some IDs were reused by new leader, Redis could not figure out if this record is new, and hence served the data. Which eventually was wrong. Redis ended up serving data from old leader.
- This caused some private data to be disclosed to the wrong users.
- Scenario:
  - Before the leader crash, the DB contained 48 rows, so id counter was 48 (1-based indexing).
  - Now, after the failover, a new leader was elected among the followers. This follower contained data only till row 40. So internally, it's ID counter was at 40.
  - Since this new leader took over, it started assigning IDs 41, 42, 43..., 48, 49, .....
  - Do you see the overlap? the old leader already had a row with 41, 42...etc and now the same ID is being used for different record.
  - To make things worse, those rows 41,42,43... from old leader were cached in Redis. Although now the DB contains different records for those same IDs, when request to Redis came for ID 41, it confidentally served it. But that data was of old record, not the new one.
  -  This meant users requesting data for the new records received data belonging to completely different (and potentially private) records from the old leader, causing a data privacy breach.

**Now, how would we solve this problem?**
- Use UUIDs instead of auto-increment keys. UUIDs are globally unique. So there is no chance of two IDs to be the same, even on a different machine.
- Approach 2: Have another dedicated service for auto-increment. That service would decide what should be the next ID number. 
- Approach 3: If a failover occurs, it should be a system-wide event. Any part of the system that holds a reference to those primary key IDs should be invalidated. So, in this case, Redis cache should have been invalidated when the failover occured.
- Approach 4: Always have one synchronous replica node. And make sure this replica becomes the new leader during failover, and then again assign another follower to be synchronous replica.

## Problems with Replication Lag
- In asynchronous replication, there's always a window of time where followers are behind the leader. Reads from followers during this window return stale data. In ideal conditions this lag is milliseconds, but under heavy load, network issues, or large write bursts it can grow to seconds or even minutes.
- If the follower is behind the leader and the client ends up reading from this follower, the client will see old/stale data. This leads to inconsistencies in the database: if we run the same query on the leader and a follower at the same time, we may get different results, because not all writes have been reflected in the follower. This inconsistency is temporary. If we stop writing for a while and wait, the followers will eventually catch up and become **consistent** with the leader. This is known as **eventual consistency**.
- The problems that arise from replication lag fall into a few well-known categories.

### Read-Your-Own-Writes Problem
A user writes something — say, updates their profile — and immediately reads it back. If the read goes to a follower that hasn't caught up yet, the user sees their old data. From their perspective, their update was lost, even though it wasn't.

**Solution**: Route reads to the leader for anything the user just wrote. A common heuristic is — if the user is reading something they could have modified, send that read to the leader. For everything else, followers are fine. Another approach is to track the timestamp of the user's last write and only route reads to followers who have caught up at least till that timestamp.

### Monotonic Reads Problem
A user makes two reads in sequence. The first read hits a follower that's relatively caught up and returns recent data. The second read hits a more lagging follower and returns older data. The user sees time go backwards — they see a newer state and then an older state.

**Solution**: Ensure a given user always reads from the same replica. You can hash the user ID to consistently route them to the same follower. If that follower goes down, they get rerouted, but under normal operation their reads are monotonically consistent.


# Multi-Leader Replication
- Single-leader Replication works well if we have a ready heavy system. But, in write-heavy systems, since the write operation always goes to the leader, the leader might become a bottleneck.
- Every write operation has to go to leader only. If the leader is very far away from the user, the write operation will have high latency, which may degrade user experience.
- This is where multiple-leader idea comes. The idea is to allow more than one node to accept writes. Whenever a leader processes a write, it must forward that data change to all the other nodes. Each leader simultaneously acts as a follower to other leaders.

**Use Cases for Multi-Leader Replication**
## Multi-datacenter operation
- If we have multiple datacenters across the globe and if we are using single-leader replication, then all writes must go to the datacenter where the leader lives. If you're in India and the leader is in the US, every write request will have to go to US.
- In multi-leader configuration, we can have a leader in each datacenter. Within each datacenter, regular leader-follower replication will be used. But, between datacenters, each datacenter's leader replicates its changes to the leaders in other datacenters. Replication between datacenters happens asynchronously in the background.

## Offline Operation
- Suppose we want to have an application that needs to continue to work while it is disconnected from the internet. For example, calendar app.
- In calendar app, we are able to see our meetings (read operation) and able to create new meetings (write operation) at any time. Doesn't matter if we are connected to internet or not. When our device comes online, the meetings sync up with the server and should be reflected on our other devices as well.
- Whenever we perform the write operation (create new meeting), it goes to local database, which acts as a leader (it accepts write requests), and there is asynchronous multi-leader replication process (meetings sync) going on between the current device, the server and my other devices with the same app.
- From an architectural point of view, this setup is essentially the same as multi-leader replication between datacenters, taken to the extreme: each device is a "datacenter". 

## Collaborative Editing
- Google Docs basically.
- When one user edits a document, the changes are instantly applied to their local replica (the state of the document in their web browser or client application) and it is asynchronously replicated to the server and any other users who are editing the same document.
  
## Write Conflicts
- If two leaders processes a write operation for the same record and the same field. It will create a write conflict.
- For example, two users simultaneously edit the same record — one through datacenter A's leader, one through datacenter B's leader. Both writes succeed locally. Now both leaders try to replicate to each other and discover they have conflicting values for the same record. What do we do?
- This is the write conflict problem, and it's the central challenge of multi-leader replication. There's no perfect solution, only trade-offs.
- Say you have a calendar event on Tuesday at 2pm. On your phone (offline) you move it to 3pm. Meanwhile on your laptop (also offline) you move the same event to 4pm. Now both devices reconnect. You have a genuine conflict, which one wins?

**Conflict Resolution Strategies**
### Conflict Avoidance 
- The approach is simple. Always route write operations for a particular data record through the same leader.
- But if that leader fails, we may have to decide a new leader for that record.

### Last Write Wins
- Each write carries a timestamp, and the most recent one wins.

### Merge the values
- For some data types you can merge conflicts meaningfully. If two users both add items to a list, you union the lists.


### Record the conflict and let the application resolve it 
- Expose the conflict to the application layer or the user and let them decide.

# Leaderless Replication
- In this architecture, there is no designated leader. Any node can accept reads & writes directly from the client. There is no single source of truth.
- There's no failover, no leader election, no single point of coordination.
- The client (or a coordinator node on its behalf) just writes to multiple nodes simultaneously.
- Dynamo (Amazon's internal key-value store), Cassandra, and Riak are the most well-known examples of this architecture. It's sometimes called the **Dynamo-style** architecture.

## How Writes and Reads Work
- Since there's no leader, how do we perform write operation? We write to multiple nodes and require a minimum number of them to confirm before considering the write successful. This minimum is called a **quorum**.
- The client (or a random node acting as a coordinator) sends writes and reads to multiple replicas simultaneously.

### Write Operation
When you want to write data (e.g., updating a user's phone number):
1. The client sends the write request to all `N` replicas in the system.
2. The client doesn't wait for all of them to respond. It only waits for a specific number of successful acknowledgments, called the Write Quorum (`W`).
3. Once `W` nodes say "Got it!", the write is considered successful.

### Read Operation
1. The client sends a read request to multiple replicas (`R`).
2. Because some nodes might have missed past writes (due to network hiccups or crashes), the replicas might return different versions of the data.
3. The client uses **version numbers** or **timestamps** to figure out which data is the newest.
4. The client waits for `R` responses before deciding what the correct value is.

## The Quorum Math

How do we guarantee that a read will actually see the latest write if nodes are allowed to miss updates? We use **Quorum Intersection**.

To ensure a read always reflects the most recent write, the number of nodes we write to ($W$) and the number of nodes we read from ($R$) must overlap. Mathematically, in a system with $N$ total replicas, we use the following rule:
$$W + R > N$$

### An Intuitive Example
Imagine a cluster where the total number of replicas for a piece of data is $N = 3$.

- Let's configure our system so that $W = 2$ and $R = 2$.
- Check the math: $2 + 2 = 4$, which is greater than $3$. The rule holds.

1. The Write: You update a key status = "Active". Node A and Node B acknowledge it. Node C is down and misses it.
2. The Read: Later, you read from 2 nodes ($R=2$), and you happen to hit Node B and Node C.
3. The Result: Node B gives you "Active" (with a new timestamp). Node C gives you null or an old value. Because Node B and Node C overlapped on Node B, your client sees the new timestamp and knows "Active" is the true reality.

### Configuring $N$, $W$, and $R$
- The parameters $N$, $W$, and $R$ are typically configurable.
- A common choice is to make $N$ an odd number (typically 3 or 5) and to set $$W = R = (N + 1)/2$$
